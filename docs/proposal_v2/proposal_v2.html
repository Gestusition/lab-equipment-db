Abstract

This revision keeps the subject of the October proposal, a PostgreSQL database for university laboratories and shared scientific equipment, and answers the feedback that its scope was too narrow. No new topic is introduced. The same domain is modelled in more depth and split into six modules: organisation and people, inventory, training and authorization, booking, service, and finance, with an audit and security layer underneath. The EER model grows from 11 to 31 entity types. It now uses overlapping as well as disjoint specializations, a category (union type), a weak entity, a ternary relationship, recursive and one-to-one relationships, and composite, multivalued and derived attributes. Two items that v1 listed as future work, transfer history and usage charging, are now in scope. The implementation is entirely in SQL and has been built and tested on PostgreSQL 18. A reproducible test suite of 111 positive, negative and concurrent cases passes. The extended EER diagram is submitted as a separate PDF; this document contains no program code.

1Introduction

Shared laboratory equipment is expensive and is used by researchers from several projects. When inventory, training, bookings and service history are kept in separate spreadsheets, the records become inconsistent and bookings conflict. A relational database can centralise these records and make the operational rules explicit [1, 2]. The October proposal covered this core with eleven entity types. The feedback was that this scope was limited, so this revision deepens the same domain rather than replacing it.

The design is organised as six modules. Each module is a PostgreSQL schema and a script of its own, loaded in dependency order, so it can be explained, tested and graded separately:

The v1 rules are unchanged. Booking times must be valid, and blocking reservations of one item must not overlap. The booker must be a project member for the whole booking. Training-required equipment also needs a valid equipment-specific authorization. Every active project has exactly one current principal investigator. Each reservation has at most one usage log, and availability is derived. The new modules add rules of the same kind. Hazardous items need a passed safety course for their own hazard class and the lab manager's approval. Equipment may only be housed in a laboratory with an adequate biosafety level. A critical incident takes an item out of service immediately. A charge must fit the remaining budget of a grant of the same project. Historical records cannot be deleted or rewritten. A graphical interface, IoT integration and procurement remain out of scope.

2Procedure

  1. Refine the EER model: keys, cardinality ratios, participation, specialization and category constraints. Map each construct to relations, choosing the mapping per specialization: single relation with a discriminator (option 8C) for the v1 equipment split, and one relation per subclass (8A) for the overlapping and attribute-defined specializations. The category uses a surrogate key [1]. Document functional dependencies and verify BCNF for every relation, rather than assuming it from the presence of keys [2].
  2. Implement each module in SQL. Single-row rules use keys, CHECK and domains. Interval rules (bookings, authorizations, rate periods) use exclusion constraints over range types [4]. Cross-table rules use triggers and stored procedures. Rules that may be violated temporarily inside a transaction use deferred constraint triggers: principal-investigator replacement, specialization totality and category attachment. A change in one module re-validates future bookings: a membership that ends, a revoked authorization, a newly introduced training requirement, or retired equipment.
  3. Add the security layer: four group roles with least-privilege grants, SECURITY DEFINER booking functions as the only write path for researchers, row-level security on reservations, and an append-only audit log partitioned by month.
  4. Build reporting views: availability, calibration status, expiring authorizations, utilisation ranking (window functions), reliability (mean time between failures and to repair), service cost subtotals (ROLLUP), grant budget, category and advising trees (recursive queries), and a materialized monthly utilisation view. Select indexes from access patterns and confirm them with measured query plans.
  5. Load a reproducible dataset in which the "current time" is fixed, so that time-dependent rules give the same result on every run. Execute the test suite. Every test runs in a rolled-back subtransaction and records expected versus observed outcomes. Concurrency tests open two real sessions to check that conflicting bookings and the last seat of a training session are serialised correctly.

3Theory

Specializations. Let E be EQUIPMENT. The v1 specialization is unchanged: with T and U the training-required and unrestricted subclasses,

T ⊆ E,   U ⊆ E,   E = T ∪ U,   T ∩ U = ∅,

selected by the mandatory Boolean discriminator training_required. A second, independent specialization of the same superclass is added. With H hazardous and C calibratable equipment, H ⊆ E and C ⊆ E hold, but neither H ∩ C = ∅ nor H ∪ C = E is required: the specialization is overlapping and partial. A gamma counter is in both subclasses, while a benchtop centrifuge is in neither. PERSON is specialized in the same overlapping, partial way into ACADEMIC, GRAD_STUDENT and TECHNICIAN; a lecturer who is also a PhD student belongs to two subclasses. MAINTENANCE is specialized disjointly and totally into PREVENTIVE and CORRECTIVE by the attribute maintenance_type.

Category. An equipment owner is a department, a laboratory or a funding grant. Its members come from three different superclasses, so this is a category (union type), not a specialization: OWNER ⊆ DEPARTMENT ∪ LABORATORY ∪ GRANT. The category is partial, because not every department owns equipment. It is mapped with a surrogate key whose kind travels inside each superclass's foreign key, so one owner can never be claimed by two superclasses [1].

Ternary relationship. AUTHORIZATION relates a trainee, an assessor (both PERSON) and a TRAINING_REQUIRED_EQUIPMENT. "Who certified whom on which instrument" cannot be reconstructed from the three binary projections, so the relationship is kept ternary. It participates with the subclass T, not with E, which makes an authorization on unrestricted equipment impossible by construction.

Weak entity. An equipment component is identified by its instrument and a component number. The component number alone is only a partial key: component 1 of the LC-MS and component 1 of the confocal microscope are different rows.

Temporal integrity. Reservations, authorizations and rates are valid over intervals. For two blocking reservations r, s of the same item the database guarantees period(r) ∩ period(s) = ∅, using half-open intervals so that back-to-back bookings are allowed. Because the check is an index-backed constraint and not an application-side query, it also holds under concurrent transactions [4].

Normalization. Every relation has been checked for partial and transitive dependencies. All non-trivial dependencies have a candidate key on the left, so the schema is in BCNF. Stored derived values are either generated columns, which the DBMS keeps consistent, or deliberate historical snapshots, such as the hourly rate at the time of use.

4Results

Unlike in v1, results are now measured rather than expected. The implementation consists of 37 tables (plus 13 monthly audit partitions), 63 triggers, 56 functions and procedures and 17 reporting views. It builds from an empty database with a single script. The test suite contains 111 cases: 15 organisation, 17 inventory, 10 training, 33 booking, 13 service, 10 finance, 5 audit, 6 security and 2 concurrency tests. All of them pass. Negative tests cover the v1 list (duplicate identities, absent parents, invalid dates, overlapping bookings, expired authorization, invalid membership, a second usage log, activation without a principal investigator) and the new rules: subclass and category integrity, cycles, biosafety levels, calibration, budgets, history protection, privileges and row-level security. In both concurrency tests the second session demonstrably waited for the first one's lock and was then rejected.

Query plans recorded on 200,000 generated reservations show that the composite expression index answers a researcher's "latest bookings" query in about 0.03 ms. Without it the same query takes about 140 ms through a parallel sequential scan. The partial approval-queue index occupies 16 kB, against about 11 MB for a full B-tree on the same table. The plans also show that the exclusion constraint's GiST index can be reused for availability queries only when the query repeats the constraint's status predicate. This finding is reflected in the reporting views.

5Remarks and Recommendations

This is an individual project. All software remains in SQL inside the database. The scripts, the generator of the EER drawings, and the test and measurement scripts are kept in a version-controlled repository with one commit per module. The application-level identity used by row-level security and the booking functions is a session setting. A production system would bind it to authenticated database logins. Possible further work within the same domain includes several membership intervals per person and project, booking rules per laboratory (opening hours, maximum duration), and notification queues for expiring authorizations and calibrations.
